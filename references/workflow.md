# 八步流程的执行细节

主文件 SKILL.md 里那张表说的是每一步在判断什么，这份文件说的是怎么做。
需要具体参数、需要知道输出该怎么读、或者撞上了边界情况，翻到对应那一步。

一次不必全读。你在第几步，就读第几步。

---

八步。前面每一步没做完，后面的数字都不成立。

```
1  体检   这张表长什么样 —— 结构、类型、脏点。先看再算
2  清洗   变成规范分析表，每一步可追溯可回放
3  对齐   摸底 → 查外部基准 → 告诉用户 → 问清他要什么 → 定口径
4  分析   扫陷阱，走配方，每条发现都推到「所以呢」
5  对账   行数守恒、总和守恒、与表内合计交叉验证、抽样回溯源单元格
6  交付   Excel / 图表 / 报告，口径随数字一起交付
7  验图   渲染出来看画错了没有
8  质控   另派一个没参与创作的 agent 从原始数据重算
```

**简单任务不必走满八步**——查一个数、改一个公式、做一张干净表的透视，直接做。
判断标准：这个数字会被别人拿去做决定吗？会，就走完对账。

### 第 1 步 · 体检

```bash
python3 scripts/profile_table.py <文件> [--sheet 名称] [--json]
```

它先用 openpyxl 读原始单元格再动 pandas，所以能看见 pandas 看不见的东西：
表头真实位置、多级表头、合并单元格、混在明细里的小计行、脚注行、隐藏行列、
文本型数字、伪装成文字的缺失值（—、N/A、无）、日期的多种写法、全角空格。

输出里的「必须先处理」清空之前，不要开始算任何业务数字。

### 第 2 步 · 清洗

```bash
python3 scripts/clean_table.py <文件> [--out 输出.xlsx] [--dedup] [--dry-run]
```

目标是 Tidy Data（Hadley Wickham）：**每个变量一列，每条观测一行，每类观测单位一张表**。

它按体检结果自动处理：取正确表头、排除汇总与脚注行、ffill 恢复合并单元格、
文本型数字转数值、伪装的缺失值归一、去首尾与全角空格、日期统一 ISO。
每一步报告影响了多少行，并**额外生成一份等价的 pandas 脚本**——
只给结果的清洗是黑箱，三个月后没人说得清第 47 行为什么不见了。

**它不猜。** 认不出格式的日期、转不成数字的值，一律原样保留并列进
「没能自动解决」，交给你看。静默猜测是数据分析的头号杀手。

去重默认不做：重复行可能是真实业务（同一天两笔同额订单），也可能是粘贴事故，
这是业务判断不是技术判断。确认之后再加 `--dedup`。

五种脏形态的分类学和手工修法，见 `references/dirty-data.md`。

### 第 3 步 · 对齐

**这一步是整个流程里最容易被跳过、跳过后损失最大的一步。**

用户开口的时候，往往还不知道自己要什么——因为他也没看过这份数据长什么样。
「帮我分析一下我的数据」是他此刻能给出的最诚实的表述。
你这时候去问「你想分析什么维度」，他只能瞎猜，猜出来的还得你去实现。

所以澄清不放在最开始，放在**你已经看懂数据、他也能看懂你的描述**之后。

#### 先出一份摸底

清洗完，用一段话讲清这份数据是什么。不要贴 `describe()` 的原始输出：

- 几行几列，覆盖什么时间范围
- 有哪些**维度**（可以拿来分组的）、哪些指标（可以拿来求和平均的）
- 关键指标的量级和分布形态（偏不偏、集中不集中）
- **一到两个已经能看到的现象**——这一条最重要，它证明你真的看了数据，
  也最容易勾出用户脑子里真正关心的问题

#### 再查一遍外部基准（领域专家的活）

摸底只说明「你的数据长这样」，用户真正想知道的是「这样算好还是不好」。
这两个问题之间隔着一个外部基准，而基准不在他给你的文件里。

- 这份数据属于哪个平台 / 行业 / 业务类型？
- 该行业这些指标的中位数、头部水平、及格线分别在哪？
- 最近有没有平台规则或行业变化，会让历史基准失效？

**能联网就去查**，优先平台官方数据、行业报告、公开的头部案例。
查到了就把「你的值 vs 行业基准」并排放进摸底里——
用户看到这一栏，才知道该往哪个方向问问题。

查不到或环境不能联网，就明确写一句「本次没有外部基准，以下都是内部对比」。
让他知道缺了什么，比让他以为分析是完整的重要。

#### 然后带着摸底去问他

问题要具体到能直接回答，别问开放题：

- **你想回答的问题是什么？** 他答不上来就给 3 个候选，
  每个候选说清「回答了它你能做什么决定」
- **这份分析要拿去做什么决定？** 决定不同，该看的维度完全不同
- **有没有我从数据里看不出来的背景？** 改版、活动、口径变更、异常事件——
  这类信息只有他有，而它们经常是异常值的唯一解释
- **哪些维度对你有意义，哪些是噪音？** 你看到 12 个维度，他可能只关心 3 个
- **要出报告的话：有没有此前的报告、PPT 或文档规范可以参考？** 有就请他发来，
  解析与模仿的做法见第 6 步「有现成规范时：解析出规范再模仿」。
  读者习惯的长相比你的品味优先

**问完等回答再往下走。** 这是少数几个值得停下来的地方——
带着错的问题做完整套分析，返工成本远高于等这一次。

他要是说「你看着办」，那就自己定，但**把你定的写出来**：
「我按 X 来做，因为 Y。不对的话现在说，做完再改代价大。」

#### 最后钉死口径

| 项 | 要回答的问题 |
|---|---|
| 指标定义 | 「销售额」含不含退款、税、运费 |
| 时间窗口 | 哪天到哪天，按下单还是按支付 |
| 分母 | 环比的上期是什么，占比的整体是什么 |
| 单位 | 元还是万元（列名和实际值经常不一致，体检会报） |
| 去重 | 重复行是真实业务还是粘贴事故 |
| 排除 | 哪些行不算，为什么 |

口径变了数字就变，且两个数都对。所以口径必须跟着数字一起交付。

**数据回答不了他的问题时，立刻说。** 他问「哪个渠道带来的用户留存最好」，
但表里没有用户 ID 没法追踪留存——这时候要马上讲，不要做一个近似的东西
交上去让他以为问题被回答了。

### 第 4 步 · 分析

先扫一遍陷阱，再开始下结论：

```bash
python3 scripts/scan_traps.py <清洗后的文件> [--min-group 30]
```

它检测的是**「数字算对了但结论错了」**那一类问题：辛普森悖论、幽灵分组、
小基数百分比、时间断点、双峰分布、极端集中、伪维度。
这些逃得过对账——对账只能证明算得对，证明不了结论对。

然后确定问题类型，选配方。配方库在 `references/analysis-recipes.md`：
对比 / 趋势 / 构成 / 分布 / 相关 / 异常 / 漏斗 / 留存 / 归因。

**每条发现都推到「所以呢」再停。** 分析师交付「完播率分成了零重叠的两堆」，
顾问交付「两堆的区别是选题类型，所以下一批全押 A 类，
预计把平均完播率从 X 抬到 Y」。问不下去了，才是可交付的深度。

推的时候带上第 3 步查到的外部基准：「这个数比行业中位数低 8 个点」
比「这个数比上月低 8%」有用得多——前者指向该不该改，后者只说明变了。

要出洞察和报告（而不只是几个数），读 `references/insight-report.md`：
多视角怎么选、怎么综合、金字塔结构怎么搭、什么算洞察什么只是描述。

每类配方都带它的陷阱。最常踩的四个：

- **辛普森悖论**——分组内都上升，合起来却下降。看总量必须同时看分组
- **幸存者偏差**——只统计还活着的样本，结论会系统性偏乐观
- **回归均值**——上期最好的这期变差，往往不是策略失效而是统计规律
- **用同一份数据既生成假设又验证假设**——探索和验证必须分开，否则任何噪音都能被讲成规律

区分你在做哪件事：**探索**是找出好问题，推断是给出可对外声称的答案。
两者的证据强度不同，措辞也必须不同。

### 第 5 步 · 对账

```bash
python3 scripts/verify_numbers.py <文件> [--claim "列名:数值"]
```

做四件事：行数守恒审计、与表内合计/小计交叉对账、去重影响量化、单位量级校验。
退出码 0 = 全通过，1 = 有对不上的，可以直接当流水线闸门。

它遵循 ICAEW《Financial Modelling Code》的 master check 思路：
一个总检查，任何一项失败就报警，不通过就不准交付。

**没有合计行可对时**，人工抽查至少 3 个数字回溯到源单元格，并在交付物里写明
「本次结果无独立校验来源」。不要沉默地交付一个没验过的数。

### 第 6 步 · 交付

数字和口径一起交付。

**图表**：先让它推荐，再生成。

```bash
python3 scripts/make_chart.py <文件> --suggest
python3 scripts/make_chart.py <文件> --x 门店 --y 销售额 --type bar --title "写结论不写主题"
```

图表的第一步不是选类型，是**把要传达的信息写成一个完整的句子**——
那句话既决定图表形式，也就是图表标题。写不出那句话，画的就是装饰。

生成时会自动执行诚实性约束：柱形图数值轴强制从 0、类别按值排序、
单系列去图例、类别过多自动聚合、**类别超过 3 类时拒绝生成饼图**
（饼图靠角度和面积编码，感知精度低于条形图的长度编码，这有实验数据）。

判断依据和完整的诚实性检查清单见 `references/charts.md`。

**写 Excel** 时遵守 `references/excel-craft.md` 的工程约定：
用公式不用硬编码的值、输入与计算与输出分区、假设集中放、加检查单元格、
引用可追溯、不做不必要的四舍五入。

**报告**：HTML 和幻灯片直接写，不要套模板（见 SKILL.md「报告：直接写」）。
下面这套脚本用于 xlsx / docx，或作为「某个结构该怎么写」的参考实现。

**先把图表和必要的分析做完，再决定用什么形态交付。**
形态是包装，包装不该影响里面装什么。

走脚本生成 html/deck 时的最小用法：

```bash
python3 scripts/make_report.py --template > spec.json   # 拿模板，填洞察
python3 scripts/make_report.py --spec spec.json --format html --out 报告.html
```

**同一份 spec 出四种形态**，`--format` 决定给哪一种：

| 形态 | 产物 | 什么时候用 |
|---|---|---|
| `html` | 自包含网页 | 默认。发链接或发附件，对方点开就能看 |
| `deck` | HTML 幻灯片 | 要在会上过一遍。← → 翻页，浏览器打印即得 PDF |
| `xlsx` | Excel 内的报告 | 对方要在表里继续动手——改数字图会跟着变 |
| `docx` | 六页纸文档 | 要被逐字读、被批注、被存档的正式文档 |

选哪种取决于**这份东西接下来会被怎么使用**，不是取决于哪种好看：

- 他要转发给别人看 → `html`
- 他要拿去开会讲 → `deck`
- 他要自己改数、加列、下钻 → `xlsx`
- 要走审批流、要被逐条批注 → `docx`

不确定就出 `html`，并说一句「要开会讲我可以出一版幻灯片，
要在表里继续算我可以出 Excel 版」。**同一份 spec 换个参数就行，
不用重做。**

`docx` 走的是 Amazon six-pager 的路子：**叙述体，不用项目符号**。
bullet 允许你把没想清楚的东西并列摆着蒙混过关，完整段落会逼你写出因果
和取舍。所以生成 docx 时 summary 会被合成段落——这是刻意的，不是 bug。
你在写 spec 时就该按能读成段落的方式写。

**docx 的图表会以 PNG 内嵌正文**（经 playwright 渲染，和 HTML 版同一套图），
数据表进附录供引用。环境缺 playwright 时降级为纯数据表，并在文档开头明说。
给决策者的 Word 零可视化站不住——五场压测一致的判决，别把降级当成常态。

`deck` 的文案口吻是**分析师向决策者汇报**：页标题写结论带数字；
解读用中性的专业动词（下降/收窄/贡献），不用口语化表达（亏掉/撑不起/在动）；
脚注只写口径与出处，推导过程进备注或附录页，不上正文页。
版式不用管——生成器按「结论标题＋全宽大图＋底部脚注条」排，
解读超过两段才转左右分栏。

四种形态都自包含：`html`/`deck` 无 CDN 无外部字体，`xlsx`/`docx`
是标准 Office 文件（docx 手写 OOXML，连 python-docx 都不需要）。

设计是**你的判断，不是用户的选择题**。看过数据、知道读者是谁、
知道这东西拿去干什么，档位和调子就定了。**没有内置风格可挑**——
动手前先落一份设计计划（色 / 字 / 数字 / 间距 / 版式五段），
把取值填进 `custom_style`。

**但要把判断说出来**——一句话讲清选了什么、为什么。用户看到理由才知道
你不是随手挑的，不同意也能一句话改掉。设计计划怎么写、
十五条不许长成的样子，见 `references/report-styles.md`。

#### 有现成规范时：解析出规范再模仿

第 3 步问到「有此前的报告 / PPT / 文档规范」且他发来了样例时，走这条路。
它覆盖上面「风格是你的判断」——读者已经习惯的长相，优先级高于你的品味。

**第一步：把样例读完。** docx/pptx 是 zip 包，解出 XML 能拿到色值、字体、
母版信息；图片或 PDF 版式逐页看。只翻前三页就开始写规范，等于没解析。

**第二步：写成一份规范文档**——单独一份交付物，像口径声明一样，四层：

1. **结构层**：章节清单与顺序；有没有封面、目录、执行摘要；各章篇幅比例；
   结论放前还是放后；附录收什么。多份样例不一致时以最近一份为准，并注明
2. **视觉层**：主色/辅色的具体色值（从样例文件里吸取，别目测）；
   字体与字号层级；页眉页脚和 logo 的位置；表格线框风格；
   留白密度——一页塞几个元素
3. **图表层**：他们惯用哪几种图型；数据标签打不打、打在哪；单位习惯
   （万元还是千元、百分比几位小数）；正负值配色（红涨绿跌还是反过来）
4. **用语层**：固定称谓与术语（「本行」「集团」，「Q3」还是「三季度」）；
   结论句式（「建议……」「应……」还是只陈述）；语气正式度；
   正文里数字怎么写（要不要千分位、阿拉伯还是汉字）

**每条规范都要能指回样例的具体位置**（第几页 / 哪一节）。
指不回去的是你的臆测，删掉。

**第三步：拿规范找他确认再动手**，重点确认两类：
样例之间互相矛盾的地方（你选了哪个、为什么），和你打算不继承的地方（见下）。

**不继承清单**：样例里违反「不能丢的底线」的做法——双轴图、截断轴、
无口径数字、误导性配色——模仿风格不模仿错误。每处偏离在交付物里注明
「此处与既有版式不同，因为 X」，让他知道是有意的，不是没学像。

**PPT 的场合**：解析照做，deck 生成仍在 huashu-design——把这份规范文档
作为第四样随交接带过去（见「幻灯片和 PPT：交给 huashu-design」）。

口径声明、边界声明、图表诚实性约束是结构性的，不由你决定要不要写；
缺了脚本会警告。

**要定期做的分析，交付模板而不是报告。** 如果这件事每月都要来一次，
正确的产物是一个能一键刷新的 Excel 模板，做模板的时间第二个月就赚回来了。

### 第 7 步 · 验图

```bash
python3 scripts/verify_visual.py 报告.html --shots 自检     # 退出码 1 = 有 FAIL
python3 scripts/verify_docx.py   报告.docx                  # 退出码 1 = 有 FAIL
```

**怎么读 `verify_visual.py` 的输出**——它的两类结果可信度差得很远：

| 检查项 | 实测可信度 | 怎么对待 |
|---|---|---|
| 元素越出 viewBox、文字重叠、被遮挡、控制台报错 | **高，逐条都是真的** | 全部修掉。它抓到过 `<svg height="auto">` 这种肉眼完全看不出、图还照常渲染的非法属性 |
| **图上数字与正文数字「接近但不相等」** | **低到接近于零** | 误报率极高，逐条看一眼就行，别为它改数字 |

它会把这些都当成「正文里的数字」：SVG 的几何属性（`cx="318.1"`）、CSS 里的 `@page{size:297mm}`、
坐标轴整刻度（110/115/…/140）、日期里的四位年份、甚至法律判例的卷页号
「433 U.S. 299, 311」。**知道这一项不可信，比修它更重要**——
不知道的人会跑三五次之后开始整片跳过 WARN 区，然后连真 FAIL 一起漏掉。

它还有两个已知盲区，要靠你自己看截图补：

- **只对 100% 重叠敏感**，30–60% 的部分重叠不报——而后者肉眼一样刺目
- **看不见 `aria-label` 和 `<title>` 里的数字**。图注和正文都对、只有 `aria-label`
  里的数字写错，这种它一个字都不会报

`verify_docx.py` 相反，是这套工具里最诚实的一个。它缺字体时会明说
「跳过 1 项（工具缺失，**不等于通过**）」并指出是哪一项——
**看到「跳过」不要当成绿灯**。另外它在 macOS 上首次调用 LibreOffice 可能报
`Task policy set failed: 4`，原因是需要可写的 `HOME`，解法：

```bash
HOME=<某个可写目录> soffice --headless --convert-to pdf 报告.docx
```

**手写 SVG 必然会犯这几类错**——坐标是算出来的，标签位置没有布局引擎兜底，
数据一变就可能叠在一起或跑出画布。肉眼扫源码看不出来，渲染出来一眼就看见。
没装 playwright 时脚本退出码 2 并提示，那就手动开浏览器逐屏看，**别因为工具不在就跳过**。

**跑完仍然要自己看一眼截图。** 机器判「画错了没有」，判不了「好不好」：
每张图能不能独立回答它的标题、有没有该画成图却写成了段落、
首屏能不能十秒看懂核心结论——这三件事没有脚本替得了。

### 第 8 步 · 质控

派一个**没参与创作**的 agent，把交付物和原始数据一起给它。指令模板：

```
你是质控。下面是一份数据分析交付物和它依据的原始数据。
你的任务不是核对交付物和中间产物是否一致——那类抄写错误最容易发现也最不值钱。
请从原始数据独立重算至少 3 个核心结论，然后逐条回答：

1 窗口：结论依赖的时间段是不是挑出来的？换一个窗口，结论还在吗？
2 粒度：聚合得够不够细？有没有把混合效应算成了主效应？
3 基准：外部基准的分母、年份、地域，和报告里的数对得上吗？
4 声称：「已剔除某某偏差」这类话，代码里真做到了吗？

对每条给出：CONFIRMED（复算一致）/ REFUTED（复算不一致，附你的数）/
UNVERIFIABLE（数据不足以判断）。不确定就写 UNVERIFIABLE，不要猜。
```

**它报回来的每一条，自己再复算一遍再改。** 症状对不等于病因对——
典型例子：质控报「deck 的图全渲染成 0×0，因为 SVG 写了 width 100% 没定高」。
症状是真的（闸门确实报 0×0），病因是错的——真实原因是闸门量了 `display:none`
的隐藏元素。照它说的去改 CSS，会把本来正常的图改坏。

## 交付格式的坑

### Word 有四个坑，全都在生成端不报错

共同点：**你这台机器上看着好好的**，换台机器、或者读者一打开就露馅。
所以不能靠肉眼，靠 `verify_docx.py` 拦。

**一、字体只能写死一个名字，没有 fallback 链。** CSS 里写
`font-family: A, B, sans-serif` 是常识，Word 没有这个东西——`w:eastAsia`
里填什么就是什么，字体不在就静默回退成主题字体（通常是宋体）。
只能选 **Microsoft Office 在 Windows 和 macOS 上都随装**的那几款：
`Microsoft YaHei` / `DengXian` / `SimSun` / `SimHei` / `KaiTi` / `FangSong`。
`PingFang SC`、`Helvetica`、`Segoe UI` 这类都是单平台字体，别用。

> 附带一条：这个白名单的前提是**那台机器装了 Microsoft Office**。
> 纯 macOS 环境可能一款都没有，`verify_docx.py` 会如实报告
> 「渲染时本机缺字体……页数与空白页位置只是近似」——那是「没验成」，不是「通过」。

**二、中文 run 必须显式带 `w:eastAsia`。** 只设 `font.name` 只管西文，
中文会走主题字体。声明在段落样式里也行（run 会继承），但不能两处都没有。

**三、别用「空段落 + 分页符」换页。** 空段落本身占一行——上一页正好排满时，
它被挤到下一页，分页符再把正文推到再下一页，于是留下**一整页全白**。
正确写法是给标题段落设 `page_break_before`。

**四、跨页的表格要设表头重复**（`w:tblHeader`），否则第二页起读者看不到列名；
行内容不长的话再加 `w:cantSplit`，避免一行被腰斩。

图片附带一个：宽度超过版心时右侧直接被裁，生成端不报错。按版心宽度留 0.5cm 余量。

还有一条只在手写 OOXML 时会撞上：往 `[Content_Types].xml` 插
`<Default Extension="png">` 要插在 `<Types>` 开标签之后，不是 XML 声明之后——
插错位置元素会跑到根元素外面，`zipfile` 读得出来、检查脚本也能解析并报「全部通过」，
**但 Word 和 LibreOffice 直接打不开**。生成完用 `soffice --convert-to pdf` 试一次最保险。

### 验幻灯片：deck 模式会被自动识别

`verify_visual.py` 会先展开再测量：`<details>` 折叠附录一律展开；
检测到 ≥2 个藏着 SVG 的 `display:none` 容器（幻灯片的隐藏页）就进入
deck 模式——视口切 1920×1080、「页面横向溢出」降为 WARN、
`--shots` 改为逐页截图。也可用 `--deck` 强制。

这消掉了两类曾经 100% 命中的结构性误报：隐藏页包围盒必然 0×0
（被误读成「SVG 尺寸写错」）、固定页宽 deck 撞上 1100 默认视口
（被误读成「横向溢出」）。**如果闸门读数指向「所有图全坏」这种
整齐得可疑的结论，先怀疑测量方式，再怀疑图**——一个会误导的闸门
比没有闸门更糟，这两类误报当初各让一个测试写下过错误诊断。

### 幻灯片和 PPT：交给 huashu-design

**触发条件**：用户要幻灯片、PPT、deck、演示文稿——不管是 HTML deck 还是要导出 `.pptx`。

**职责边界**：本 skill 负责数据分析的内容和图表，不负责演示文稿的生成与视觉。
排版、母版、动效、封面、视觉方向是另一个专业，硬做的结果是「一眼看出是自动生成的」。

**三步**：

1. **探查** `huashu-design` 在不在——skill 目录里有没有它，或你的 skill 清单里列没列它
2. **没装就引导安装**：https://github.com/alchaincyf/huashu-design
3. **交接**，之后 deck 由它负责

**交接要给三样**，缺一样它就得重新解读数据，你上游的口径工作会白做：

| 给什么 | 为什么 |
|---|---|
| **口径声明**（第 3 步产出的那份） | 它照着用，不自己重新定义指标 |
| **论点结构**（章节标题即论点链 + 每条的证据等级） | deck 的骨架是论证，不是章节 |
| **已通过 `verify_visual.py` 的内联 SVG** | 图已验过越界/重叠，它只做版式不重画 |

用户给过报告 / PPT 模板的，**加第四样：解析出的规范文档**
（见第 6 步「有现成规范时：解析出规范再模仿」）——视觉方向直接锚定它。
但规范不豁免 huashu-design 的三方向硬门，怎么走由它自己判断。

一并说清哪些数字是定稿、哪些是估算、哪一条最脆弱。
**别把原始数据丢给它让它自己算**——口径错误会在第二个 skill 里重演一遍，
而那边没有对账闸门。

**装不上、用户不想装、或你是批量派出的 subagent 卡不进它的三方向硬门时**：
兜底走 `make_report.py --format deck`——版式按「结论标题＋全宽大图＋
底部脚注条」生成，是地板不是天花板。手写 deck 是最后选项，
写完必须过 `verify_visual.py`（deck 模式，见上一节）。
