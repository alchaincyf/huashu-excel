# 报告的设计

风格该由你来定，不该做成一道给用户的选择题。

拿一堆风格去问「你想要哪种」，等于把自己的活推给了对方。他要的是一份好报告，
不是一次挑选练习。何况你看过数据、知道读者是谁、也知道这份东西要拿去干什么——
这三件事凑齐了，设计就已经定得下来。

但要把判断说出来。一句话就够：你选了什么，为什么。
用户看到理由才知道你不是随手挑的，不同意的时候也能一句话改掉。

这份文件里没有可以直接拿去用的风格。以前有六种（咨询、投行、财经媒体、杂志、
科技公司、极简），后来删了，理由写在第八节。留下来的是方法和禁令。

---

## 一、先定档

要判断的其实不是「这份东西要不要设计」，而是要设计到哪一档。
一份对账表和一份对外洞察报告，花的心思一样多，长出来的样子不该一样。

三个问题：

**1. 这份东西要拿去做什么？**

| 用途 | 说明 |
|---|---|
| 支撑一个决策 | 有人要拿它拍板 → 结构化、编号、结论前置 |
| 汇报交差 | 对上或对外 → 正式、可打印、经得起细看 |
| 自己或团队看 | 内部快看 → 越轻越好，别装 |
| 讲一个观点 | 有立场要传播 → 叙事性、有态度 |

**2. 读者是谁，他有多少耐心？**
投资人和董事会看结构和数字密度；业务负责人看结论和行动项；
工程和产品团队看得懂图但讨厌废话；外部客户会注意你的做工是否体面。

**3. 内容本身是什么形状？**
数字密集、多张表 → 高密度；一个核心结论加少量证据 → 极简；
需要一路讲下来的逻辑链 → 叙事型。

### 两档，绝大多数落在第一档

实用档是对账、复盘、周报月报、内部分析，以及给某个具体决策用的材料。
排版层次、间距刻度、配色都要讲究，但不上花活：没有巨型首屏，没有装饰性图形，
没有动效，没有纯为了好看而存在的元素。这一档的「好」是读起来不费劲，
跟「看起来有设计感」是两件事。

表达档是对外发布、有立场要传播、对方会拿它判断你做工的场合。
可以有一个真正的首屏，也可以在某一个地方冒一次险——一个地方，不是处处。

拿不准的时候往克制那边靠。一份排版得体的报告永远不会是错误答案，
一套过度设计的视觉有时候会是。财务对账报告长得像杂志内页，那不是升级，是事故。

## 二、动手之前，先落一份设计计划

这是硬步骤。写第一行 HTML 之前，把下面五段写下来，然后照着它写，别边写边改主意。

**Color** — 4 到 6 个具名色值，每个写清楚用在哪：
底色、正文墨色、次级文字、分隔线、强调色，再加上正负语义色。
超过六个，说明你还没想清楚。

**Type** — 至少两种角色（标题 / 正文 / 数据），外加一个字号刻度。
刻度定下来就只用刻度上的值，不要临时冒出一个 17.5px。
字体不外链（见「不能丢的底线」里的自包含要求），所以是系统字体栈之间的搭配，
中文的「衬线 / 黑体」对比就是最可用的那一组。

**Numerals** — 数字怎么排。见第四节，这一段是数据报告独有的，别跳过。

**Space** — 一个间距刻度（比如 4 / 8 / 12 / 20 / 32 / 56），
加上版心宽度和定这个宽度的理由。布局用 flex/grid 的 `gap`，
不要靠每个元素各自的 margin 去拼——那种拼法会静默塌陷，也会静默翻倍。

**Layout** — 一两句话说清版式概念。

### 为什么这一步值钱

边写 CSS 边选颜色，写着写着一定会漂：第三屏的灰和第一屏的灰不是同一个灰，
强调色不知不觉用到了四种，间距里冒出 13px、15px、18px 三个都差不多的值。
它们单看都没错，合起来就是「这份东西没人管过」。
先定一套 token 再动手，可用的值就只剩那几个，想漂也漂不了。

所以这一步约束的其实是一致性，不是审美。
一致性是「有设计」和「没设计」之间，读者肉眼最先看出来的那条线，
比配色好不好看重要得多。

### 计划要落进产出物

把这份计划当注释写进 HTML 头部，颜色定义成 CSS 变量（`:root{--fg:…}`），
别把色值散落在各个组件里。好处有三个：交付之后还能追查当初为什么这么定；
改一个值全局生效；`@media print` 只需要重定义变量，不用重写组件。

打印样式对报告是真需求，读者会把它打出来带进会议室。
深色主题则不是——报告不跟随读者的系统主题，做两套只会把决策数量翻倍。

## 三、中性色要选，不要默认

纯中灰（`#808080`、`#F5F5F5` 那一挂）读起来像「没选」；
往强调色方向偏一点点色相的灰，读起来像「选过」。

底色和分隔线是整个页面上面积最大、出现次数最多的颜色。
它们究竟是被挑出来的还是顺手继承的，决定了这份报告的第一印象。
纯白和近黑本身都没问题，要紧的是它得是你挑的。

---

## 四、数字排版

这一节在通用的网页设计规范里找不到，但对数据报告，它是底线。

凡是数字会上下相邻的地方——表格、KPI、图表刻度、任何成列的数——
一律加 `font-variant-numeric: tabular-nums`。
不加的话，比例字体里 `1` 比 `8` 窄，整列数字会参差，读者没办法竖着扫下来。
这条没有例外。

同一列里的小数位必须统一。一列里出现 `12.5` 和 `12.53` 是错的，
哪怕原始数据就长这样。

单位写进表头，不要写进单元格。写「营收（万元）」然后单元格里放 `1,204`，
不要每个格子后面都拖一个「万元」。

千分位分隔符要有，四位数以上一律加。

负数怎么表示，开工前定死：`-1,204` 还是 `(1,204)`。
财务读者习惯括号，其他场景用负号。选一个，全篇一致。

数字列右对齐，文本列左对齐。数字居中是这里最常见的错误——
居中之后位数不同的数字对不齐，等于白排。

## 五、不要长成这样

没被指定风格的时候，模型会不自觉滑向几个固定的样子。
它们本身都不丑，麻烦在于它们是默认倾向而非判断的结果——
读者见得太多，一眼就知道这是随手生成的。

### A 组：通用 AI 设计陈词

1. 米黄底（`#F4F1EA` 那一挂）＋ 衬线大标题 ＋ 赤陶橙强调
2. 近黑底 ＋ 孤零零一个高饱和荧光绿或朱红点缀
3. 报纸式细分隔线 ＋ 密排多栏，假装自己是财经大报
4. 白底上的紫蓝渐变首屏
5. Inter 或 Space Grotesk 当「反正不会错」的字体
6. emoji 当章节标记
7. 什么都居中，整页找不出一条左对齐的基线
8. 圆角卡片用到底，每张卡再配一条左侧强调色竖条

### B 组：AI 数据报告特有的

9. 顶部一排四个圆角阴影 KPI 大卡，不管内容需不需要四个
10. 深蓝（`#1E3A8A` / `#1E40AF`）配浅灰底，当「专业感」的默认解
11. 章节标题前挂图标（📊 数据概览、📈 趋势分析）
12. 渐变填充的柱子和面积图——渐变在图表里不编码任何信息，是纯噪音
13. 每个结论都套一个彩色浅底的 callout 框，一整页全是框
14. Chart.js / ECharts 的出厂色板，那套半透明红蓝绿
15. 深色首屏配浅色正文，上下两段像两个不同的网站拼起来的

### 这份清单怎么用

用户明确要求某个样子的时候，照做。他说「就用米黄底衬线」，那就没得商量：
用户的话永远排在第一位，其次是他组织已有的报告规范，最后才轮到你的判断。

这份清单管的是没人指定时你的默认倾向。
在自己的设计计划里看到上面任何一条，先别急着判错，
停下来问一句：这是我为这份内容选的，还是我换个题目也会这么写？
如果答案是后者，就改掉，并且在说明理由的时候讲清楚改了什么。

## 六、图表颜色从报告的 token 派生

图表不是贴进报告里的外来物，它和报告本来就该是一套东西。
报告底色是深海军蓝、图里却冒出一组无关的蓝橙，两边各自都说得通，
合起来就不像一份东西了。

三套颜色，各管各的，不要混：

| | 用途 | 规则 |
|---|---|---|
| **强调色** | 标识性元素：标题装饰、当前项、链接 | 1 个。不用于数据 |
| **分类色板** | 图里的多个系列 | 从报告 token 派生，最多 6 类，超了合并成「其他」 |
| **语义色** | 正 / 负 / 警示 | 只用在有明确正负含义的数值上 |

语义色不占强调色的位子。强调色说的是「这里要看」，语义色说的是「这个数是负的」，
两件事。同一个红既做标题装饰又做负数，读者分不清哪个红在说话。

颜色也不表达判断。别用颜色去暗示「这个渠道不好」——那是你的结论，
该写在文字里，让读者知道那是判断而非数据。同理，别用深浅去表示「重要性」。

色板本身的规则（分类 / 连续 / 发散怎么选、为什么不用彩虹色阶、色盲友好、
灰度打印测试）在

`references/charts.md`

第五节。那边管一张图内部怎么用色，这里管它和报告的关系。

## 七、不管什么设计，这几条不变

**标题写结论。**「华东贡献六成销售额但增速垫底」，而不是「销售额分析」。
报告标题、章节标题、图表标题一律适用。

**口径声明在正文之前。** 没有口径的数字没办法被检验。

**边界声明在末尾。** 数据覆盖到哪、哪个结论最脆弱、什么没验证。
一份说出了自身弱点的报告，比一份天衣无缝的报告可信。

**图表遵守诚实性约束。** 柱形从 0、类别按值排序、坐标轴用整刻度、
不完整的末期画虚线、不画双轴。七条详见 `references/charts.md` 第四节。

**自包含。** 无 CDN、无外部字体、无网络请求，图表用内联 SVG 自己画。
离线能开、内网能开、当附件发也能开。

## 八、为什么这里不再提供内置风格

以前这份文件里有六种可选风格，每种都给了具体色值、版心宽度和 `extra_css`。
与此同时 SKILL.md 里写着「那六种是六个牢笼，不是六个选项」。

这两句话是打架的，而打架的结果从来只有一个：
描述得越具体，就越难不用它。最省力的路径永远是挑一个填进去，
于是「为这份内容设计」悄悄变成了「从六个里选一个」。
一份为咨询公司写的深海军蓝套到内部周报上，它既不认识这个读者，也不认识这份数据。

所以六种连同它们在脚本里的实现一起删了。
以后要是有人想把它加回来，先回答一个问题：
新加的这几种，凭什么比「照着这份内容想一遍」更好？

脚本里还剩一套无名的兜底缺省值。它的存在只是为了在没有设计计划时，
`xlsx` / `docx` 仍然渲染得出来，不能算一种风格。
用到它的时候脚本会警告，因为那意味着这一步被跳过了。

还有一点容易被误解：走脚本不等于这些格式不用设计。
同一份设计计划要落到三种格式上——Color 的 token 在 xlsx 里变成字色与填充色，
Numerals 变成 `number_format`，Space 变成行高与列宽，
Layout 变成合并区域与冻结窗格。
xlsx 里真正手写不划算的只有图表 API，排版全是三五行代码的事，
具体落法见 `references/xlsx-craft.md`。

## 视觉之外

设计决定这份报告长什么样，但决定它有没有用的是内容。

一份配色完美、排版精致、结论全是「A 占比 44%」的报告，
不如一份纯文本但说清了「所以预算该往哪挪」的备忘录。

洞察怎么挖、多视角怎么选、结论怎么组织，见 `insight-report.md`。
先把那个做到位，再回来做设计。
