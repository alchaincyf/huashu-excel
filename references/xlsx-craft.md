# xlsx 交付物的排版

这份文件管的是你交出去的那个 xlsx 长什么样。

别人给你的脏表怎么读、怎么洗，在 `dirty-data.md`；
Excel 公式怎么写、有哪些坑，在 `excel-craft.md`；
报告的设计怎么定，在 `report-styles.md`——那份文件说的每一条对 xlsx 一样成立，
这份只补 xlsx 独有的落法。

---

## 一、xlsx 不是导出的副产品

模型有一个几乎不假思索的默认动作：把 HTML 当成「设计出来的」，把 xlsx 当成「导出来的」。
于是同一份分析交出两副面孔——HTML 那份有配色、有层次、有节奏，
xlsx 那份是一列黑字，像是谁顺手 dump 出来的。

**它们是同一份设计计划的两种落法。** 读者拿到 xlsx 不会因为它是 Excel
就降低期待——恰恰相反，他打开 xlsx 是因为他要在里面**继续动手**，
这份东西会被他看得比 HTML 更久。

`report-styles.md` 第二节要求写第一行 HTML 之前先落设计计划（Color / Type /
Numerals / Space / Layout）。**那份计划同样是 xlsx 的施工图**，不用重写一份。

但它只有一半能直接搬过来，另一半要你现场发明——这一点写清楚比含糊带过有用：

| 设计计划的那一段 | 到 xlsx | 能不能直接搬 |
|---|---|---|
| **Color** | 字色与填充色 | ✅ 色值原样用 |
| **Numerals** | `number_format` | ✅ 小数位、千分位、负数写法逐条对应 |
| **Type** | 字号与字重 | ⚠️ px 要换算成磅，而且 xlsx 没有行高属性——行高得自己算（第四节） |
| **Space** | 行高、列宽、空行 | ❌ **没有换算关系**。HTML 的 `gap` 和 `padding` 在 xlsx 里不存在，间距只能靠空行与行高模拟，得重新定一套 |
| **Layout** | 合并区域与冻结窗格 | ❌ **没有换算关系**。版心宽度勉强能折成列宽总和，但 flex/grid 的那套结构在网格里没有对应物 |

**别把下面两行当成映射表来用**——「Space 变成行高与列宽、Layout 变成合并区域与
冻结窗格」是个类比，不是算法。真去做的时候，Space 和 Layout 这两段等于重做一遍，
只是**目标一致**：同一个视觉密度、同一个层级关系。知道要重做，比以为能照搬省时间。

### 排版自己写。但「图表交给脚本」这条分工目前接不上

手写 openpyxl 的图表 API 不划算——这话本身是对的。
但**排版不是图表**：合并、行高、列宽、字色、填充、数字格式，
每一样都是三五行代码，而且只有手写才能对得上设计计划。

问题出在另一半。`make_report.py --format xlsx` 是从 `Workbook()` 造**整个**工作簿，
`make_chart.py` 的 `build()` 同样是 `Workbook()` 输出一个**独立文件**——
两者都没有「把图插进我已经排好的工作簿」这个入口。
所以「排版自己写、图表调脚本」在工具层是走不通的，实测过，两个脚本一个都用不上。

**现状下的做法**：图也自己写。`openpyxl.chart` 的 `BarChart` / `LineChart`
连数据引用带样式一共十几行，并不比合并和行高更贵。两个坑顺带记在这里，
因为只有手写才会撞见：

- **折线图默认平滑成样条**（`series.smooth` 默认为真），
  它会**在真实数据点之间画出不存在的值**。一律显式设 `smooth = False`
- **「不完整的末期画虚线」在 Excel 原生图里做不到**——单条序列没法分段设线型。
  只能把不完整的那一期排除出图，并在图题里写明排除了什么

图表数据一律引用数据 sheet 的真实单元格区域（`Reference`），
不要把数值硬编码进图——读者改了数据，图要跟着变，那正是他要 xlsx 而不是 PNG 的理由。

## 二、先分清两种 sheet，规则几乎相反

一份交付用的工作簿通常至少两张表，它们要用两套完全不同的排版：

| | **报告 sheet** | **数据 sheet** |
|---|---|---|
| 一个单元格装什么 | 一段话、一个 KPI、一个小节标题 | 一个字段值 |
| 读者拿它干什么 | 从上往下读 | 排序、筛选、透视、下钻 |
| 合并单元格 | **该用**（见第三节） | **禁用** |
| 换行 | `wrap_text=True` 是常态 | 基本不用 |
| 行高 | 按内容算 | 统一默认高度 |
| 填充色 | 用来分区块 | 只用在表头 |
| 冻结窗格 | 一般不需要 | **必须有** |
| 自动筛选 | 不加 | 加 |

**`excel-craft.md` 第三节那条「合并单元格会破坏排序、筛选、透视」说的是数据 sheet。**
它是对的，但只对那一半成立。把它套到报告 sheet 上，
就会得到一份所有正文都挤在一列里、靠溢出往右显示的东西——
而溢出一旦撞上右边有内容的单元格，文字就被硬生生切断。

**判据很简单：这个单元格里的东西，有人会拿去排序吗？**
不会，就该合并。

## 三、合并单元格：报告 sheet 里是主力

报告 sheet 里的标题、副标题、小节标题、正文段落、脚注，
**一律合并到内容区全宽**（比如 `B2:G2`），不要只放在 B 列靠溢出。

三个理由，一个比一个实际：

1. **溢出会被挡住。** 右边任何一个单元格有内容，文字就在那里截断。
   最典型的翻车：正文段落在 B 列靠溢出显示得好好的，
   直到某一行右边放了个 KPI 数值，那一段就被腰斩。
2. **`wrap_text` 需要一个真实的宽度才知道在哪换行。** 不合并的话，
   它按 B 列那一列的宽度换行，而你眼睛看到的是横跨 B 到 G 的一整条。
   于是行高按一列宽算、文字按七列宽显示，两边对不上。
3. **合并区域是一个可测量的容器**，行高才算得准（见下一节）。

**合并前清空被吃掉的格子。** 合并只保留左上角单元格的值，
其余静默丢弃——先写值再合并会丢数据，先合并再写值才对。

**KPI 区尤其要小心。** 一个「标签在上、数值在下」的 KPI 条，
数值往往是 16pt 以上的粗体，宽度远超一列。
每个 KPI 各自合并成一个固定宽度的块（比如三个 KPI 各占 `B:C` / `D:E` / `F:G`），
让标签和数值**共用同一个合并宽度**——否则标签在 C 列、数值溢出到 D 列，
两者视觉上对不齐，读者要猜哪个数配哪个标签。

## 四、行高：算出来的，不是从档位里挑的

**这是 xlsx 排版最主要的单一错误来源。**

模型的默认动作是从一组看起来合理的档位里挑一个——`16 / 30 / 45 / 60`
之类。结果是：18pt 的粗体大标题配了 16 磅行高，字上下被切掉；
一段 70 字的正文 wrap 成三行却只给了 30 磅，底部一整行看不见。

**这类错在屏幕上很容易被忽略**（滚动时一扫而过），但读者一眼就看见，
打印出来更是明摆着。

### 🔴 一旦合并，行高就从可选变成必填

先说这条，因为它是唯一一个「不设反而更糟」的地方，而且三层防线会同时对你失效。

**Excel 不给合并单元格做自动行高。** 普通单元格开了 `wrap_text` 而不设行高，
Excel 会自己撑开；**合并单元格不会**——它按默认的 15 磅显示，多出来的行直接看不见。

于是「照第三节合并到全宽 + 开 wrap + 忘了设行高」成了一个隐蔽的坑：

| 你以为会拦住它的 | 实际 |
|---|---|
| `verify_xlsx.py` | 早期版本对「没显式设行高的行」直接跳过，一声不吭（已修，但要知道它为什么曾经漏） |
| `soffice` 转 PDF 自检（第八节） | **LibreOffice 会替合并单元格撑开行高**，渲出来一切正常 |
| 在自己机器上打开看看 | 除非用的就是 Excel，否则看不到 |

**所以：合并 + `wrap_text` 的单元格，必须显式 `row_dimensions[r].height = ...`。**
没有例外，也不要指望任何工具替你发现漏了。

### 算法

```python
import math

# 经验常数，集中在一处方便调。数值来自实测，依据见下一节
LINE_HEIGHT_RATIO = 1.42   # 单行高度 ≈ 字号 × 1.42（磅）
CELL_PADDING_PT   = 2.0    # 上下内边距
BASE_FONT_SZ      = 11.0   # 列宽单位是按 11pt 标定的
BOLD_WIDTH_RATIO  = 1.08   # 粗体宽约 8%——只影响宽度（进而影响行数），不影响行高
CAPACITY_SAFETY   = 0.93   # 容量打折，见下「行数是阶跃的」

def visual_len(s: str) -> float:
    """全角按 2，大写与数字按 1，小写按 0.75，i·l·标点按 0.45。"""
    w = 0.0
    for ch in s:
        if ord(ch) > 0x2E80:            w += 2
        elif ch in "iljI.,;:'()[]":     w += 0.45
        elif ch.islower():              w += 0.75
        else:                           w += 1
    return w

def need_height(text, total_width, font_sz=11.0, bold=False) -> float:
    """total_width = 该单元格（或合并区域）所有列的列宽之和"""
    cap = max(total_width * (BASE_FONT_SZ / font_sz) * CAPACITY_SAFETY, 1.0)
    k = BOLD_WIDTH_RATIO if bold else 1.0     # 粗体更宽 → 更早换行 → 行数可能多一行
    lines = 0
    for para in str(text).split("\n"):        # 显式换行符要分段各算各的
        lines += max(1, math.ceil(visual_len(para) * k / cap))
    return lines * font_sz * LINE_HEIGHT_RATIO + CELL_PADDING_PT
```

### 这几个常数是量出来的，不是拍的

量法很简单，可以自己复现：造一批**不合并**的 `wrap_text` 单元格
（不合并才会触发自动行高），用 `soffice --headless --convert-to xlsx` 转一遍，
再用 openpyxl 把它算出来的 `row_dimensions[r].height` 读回来。
那个值就是渲染引擎认为「这段文字真正需要多高」。

一次实测的结果（列宽固定，中文，改字号与行数）：

| 字号 | 多行时每行占多少磅 | 每行 ÷ 字号 |
|---|---|---|
| 9pt | 12.68 | 1.408 |
| 10pt | 14.18 | 1.417 |
| 11pt | 15.42 | 1.402 |
| 13pt | 17.65 | 1.358 |
| 16pt | 21.26 | 1.329 |
| 18pt | 24.99 | 1.388 |

**所以系数是 1.33 到 1.42，取上界 1.42。**

### ⚠️ 但别把自动行高当成「需要的高度」

这个量法有个陷阱，我自己踩过一次，值得写下来。

单行的实测值在 9pt、10pt、11pt 三档**全都是 16.40 磅**，看起来像是有个最小行高地板，
于是很自然会得出「9pt 单行按系数算只有 14.8 磅，不够，会被裁」。
**这个推论是错的。** 把同一个 9pt 单元格的行高压到 12.0 磅再渲染，
文字完整显示，一点没裁——那 4.4 磅是留白，不是内容。

**自动行高 ≠ 必需高度。** 渲染引擎在自动撑开时会附赠一段余量，
拿它当验收标准，会造出一大批「明明好好的却被判不合格」的误报。

所以这里不设最小行高地板，也不要因为看到 16.40 这个数就去加一条。
**量出来的数要再验一次「少给会不会真出问题」，才算量完。**

**粗体不影响行高，只影响宽度。** 实测 11pt 和 18pt 的粗体多行，
行高与非粗体一模一样（46.25 / 99.95 两组完全相同）。
所以 `BOLD_WIDTH_RATIO` 只该乘在文本宽度上——它让文字更早换行、行数可能多一行，
但每一行的高度不变。乘到高度上是重复计算。

**行数是阶跃的，所以余量要加在容量上，不是加在高度上。** 「宁可高一点」
只保护得了高度：文本 69 个宽度单位撞上 68.5 单位的容量，`ceil` 直接少算一整行，
再乘多大的行高系数也补不回来。所以 `CAPACITY_SAFETY` 打在分母上。

**这仍然是估算不是精算**：真实换行取决于字体度量，openpyxl 拿不到。
算出来的行数落在整数边界附近时（比如 1.95 行或 2.02 行），
**那一格就是不可靠的，去看一眼渲染结果**，别信任何一个数字。
`verify_xlsx.py` 会把这类单元格单独标出来，就是因为在那里它自己也不确定。

**不设 `wrap_text=True` 的单元格不要算这个**，它不换行，
一行的高度够就行；但它会溢出，回到第三节的问题。

### 空行是间距，不是遗漏

xlsx 没有 `margin`，节与节之间的呼吸靠**空行 + 行高**。
`report-styles.md` 定的间距刻度在这里落成空行的高度：
小节之间给一个 12 磅的空行，大节之间给一个 20 磅的，不要一律用默认的 15。

## 五、列宽与数字格式

**列宽先定用途再定值。** 报告 sheet 的内容列（合并后的总宽）
对应 HTML 里的版心——中文每行 38 到 42 字最舒服，
折算成列宽单位约 76 到 84。
数据 sheet 的列宽按该列最长值算，加两个字符余量。

**A 列留一个宽度 2 的窄列当左边距**，让内容不贴着窗口边——
这个做法是对的，别因为它看起来「浪费一列」就去掉。

### 数字必须设 number_format

单元格里存 `9351342.370000001` 而 `number_format` 是 `General`，
Excel 就会把那一长串原样显示出来。**这不是显示 bug，是没设格式。**

```python
cell.value = 9351342.37          # 底层值保持精确，不要 round()
cell.number_format = '#,##0.00'  # 显示层控制小数位
```

常用格式串：

| 场景 | 格式串 |
|---|---|
| 金额（整数） | `'#,##0'` |
| 金额（两位小数） | `'#,##0.00'` |
| 带币种 | `'£#,##0'` / `'¥#,##0.00'` |
| 百分比（一位小数） | `'0.0%'`（**值要存 0.058 不是 5.8**） |
| 负数用括号 | `'#,##0;(#,##0)'` |
| 日期 | `'yyyy-mm-dd'` |

`report-styles.md` 第四节那几条（同列小数位统一、千分位、单位进表头、
负数表示法全篇一致、数字列右对齐）在 xlsx 里逐条照用。
**openpyxl 里数值默认就是右对齐**——别手贱把它设成居中。

**列宽不够时 Excel 显示 `####`。** 数值按格式渲染后的字符串长度
（含千分位、币种符号、负号）要能装进列宽，
大字号的 KPI 尤其容易撞线。

## 六、色彩：xlsx 多了一种 HTML 没有的手段

xlsx 的字色用法和 HTML 一样，但它多了**填充色**——
整行整块地铺底色，这是 xlsx 分区最有效的工具，也是最容易滥用的。

**颜色全部从设计计划的 token 派生**，不要在 xlsx 里另开一套。
`report-styles.md` 第六节「三套颜色各管各的」在这里同样成立。

四条落法：

- **表头** = 深色填充 + 反白粗体字，或浅色填充 + 墨色粗体字。选一种，全簿一致。
- **区块分隔** 用极浅的填充（token 里那个 `--wash` 一级的颜色）铺整行，
  不要用边框画框——xlsx 里的框线一多就像财务报表模板。
- **斑马纹**只在数据 sheet 用，且只在超过 20 行时用。报告 sheet 不用。
- **语义色**（正 / 负）通过条件格式或 `number_format` 的颜色段实现，
  比如 `'#,##0;[Red]-#,##0'`。

### 同级别的东西必须长得一样

这是 xlsx 里最常见的层级事故：七个小节标题都是 13pt 粗体，
其中两个用了强调色，另外五个是墨色。**读者跟的是视觉，不是你的意图**——
他会以为那两个是更高一级。

写完之后做一次机械自查：把所有单元格按 `(字号, 是否粗体)` 分组，
同一组里出现两种以上字色，就是层级漏了。

## 七、数据 sheet 的四条底线

给人「继续动手」的那张表，反而最容易被裸着交出去：没列宽、没表头样式、
没冻结、没筛选。它是全簿最实用的一张，别让它最难用。

1. **首行冻结**（`ws.freeze_panes = "A2"`），左侧有标识列时冻结到 `B2`。
   **注意冻结点要落在真实内容上**——内容从 B2 开始却冻结 A2，
   冻的是一行空白，等于没冻。
2. **表头有样式**：粗体 + 填充 + 与正文可区分。
3. **加自动筛选**：`ws.auto_filter.ref = ws.dimensions`。
4. **列宽按内容算**，不要留一堆默认 8.43 的窄列让读者自己拖。

数据 sheet 里**不要有合并单元格、不要有小计行混在明细里、不要有脚注行**——
你在 `dirty-data.md` 里骂过的那些脏法，别自己造一遍交出去。

## 八、验收

```bash
python3 scripts/verify_xlsx.py 交付物.xlsx     # 退出码 1 = 有 FAIL
```

它机械地拦这几类：行高装不下 wrap 后的文本、合并单元格开了 wrap 却没设行高、
数值列宽不足会显示成 `####`、未合并的长文本右边有内容会被挡、
合并区域吃掉了非空单元格、浮点没设 `number_format`、冻结窗格落在空行上、
同级标题字色不一致。

**跑完仍要自己看一眼渲染结果。** 这句话在别的闸门那里是句提醒，
在这里是硬要求——三场压测下来，**四类真实缺陷里有三类是闸门全绿之后靠看图发现的**。

```bash
soffice --headless --convert-to pdf 交付物.xlsx
pdftoppm -r 120 -png 交付物.pdf 页
```

### 但要知道 LibreOffice 和 Excel 不是一回事

**「用 soffice 渲过了」不等于「在 Excel 里没问题」。** 已知的分歧至少有一处，
而且正好在最容易出错的地方：**合并单元格的自动行高，LibreOffice 会撑，Excel 不撑**
（见第四节）。所以一份漏设行高的文件，闸门可能放过、soffice 渲出来也好看，
用户在 Excel 里打开却是被裁的。

结论不是「别用 soffice」——它仍然是目前最好用的自检手段，
上面说的那三类缺陷都是它照出来的。结论是**知道它的盲区在哪**：

- 它照得出：文字被裁、列宽不足、溢出被挡、层级混乱、配色和分区效果
- 它照不出：合并单元格漏设行高（它会替你撑开）、Excel 专有的显示行为

**能在真 Excel 里开一眼，就开一眼**，尤其是报告 sheet 那几页。
两样都没有就明写「本次 xlsx 未做视觉自检」——
不要因为闸门全绿就当作看过了，闸门查的是可测量的错，不是全部的错。

## 九、不要长成这样

对应 `report-styles.md` 第五节，xlsx 特有的默认倾向：

1. **整份报告挤在 B 一列里**，靠溢出往右显示
2. **行高从 `16 / 30 / 45` 里挑**，而不是按内容算
3. **零填充色**，全靠字色做层级，一屏扫下来主次是平的
4. **数值直接扔进单元格**不设 `number_format`
5. **给正文段落画满四边框线**，长得像九十年代的财务模板
6. **每个 sheet 都叫 `Sheet1` / `Sheet2`**，或者叫 `数据`——
   sheet 名是导航，写「客户分层明细」不写「数据」
7. **把 HTML 报告的文字整段复制进单元格**——xlsx 的一格装不下一屏的话，
   该拆成几行，或者干脆承认这部分只适合 HTML
8. **网格线留着**。报告 sheet 关掉（`ws.sheet_view.showGridLines = False`），
   数据 sheet 留着

第 8 条是分界线画得最清楚的一条：**关掉网格线的那一刻，
这张表从「一个电子表格」变成「一份文件」。**
