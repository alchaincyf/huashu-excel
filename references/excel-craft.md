# Excel 手艺

分成三部分：现代函数体系（用 Excel 解题）、工程约定（用代码写 Excel）、
那些不知道就会中招的坑。

---

## 一、现代 Excel：先忘掉 VLOOKUP

Excel 在 2021 年之后变了。动态数组、LET、LAMBDA、以及 2024 年进入
Microsoft 365 的 GROUPBY / PIVOTBY，让 Excel 从「电子表格」变成了真正的分析工具。

**版本要求**：完整的现代函数集需要 Microsoft 365 或 Office 2024。
写公式给别人用之前，先确认对方的版本——在旧版里这些函数全部返回 `#NAME?`。

### 解题的默认顺序

查找用 XLOOKUP，取数用 FILTER + SORT，公式整洁用 LET，逻辑复用用 LAMBDA。

### XLOOKUP 取代 VLOOKUP

```excel
=XLOOKUP(查找值, 查找区域, 返回区域, [找不到时], [匹配模式], [搜索模式])
```

比 VLOOKUP 好在哪：
- 可以向左查找（VLOOKUP 只能向右）
- 直接指定「找不到时」返回什么，不用套 IFERROR
- 插入列不会错位（VLOOKUP 的第三个参数是写死的列序号，插一列就全错）
- 默认精确匹配（VLOOKUP 默认近似匹配，是最经典的静默错误来源）

VLOOKUP 那个 `TRUE` 默认值坑了三十年人：忘了写第四个参数，
它会返回「最接近的较小值」而不是报错。**这是无声的错误答案。**

### FILTER / SORT / UNIQUE：动态数组

```excel
=FILTER(A2:D100, (C2:C100="华东")*(D2:D100>1000), "无匹配")
=SORT(FILTER(...), 2, -1)
=UNIQUE(B2:B100)
```

多条件用 `*` 表示与、`+` 表示或。结果自动溢出（spill）到相邻单元格，
源数据变了结果自动更新。

引用整个溢出区域用 `#`：`=SUM(E2#)`

### LET：给中间步骤起名字

```excel
=LET(
    销售额, SUM(B2:B100),
    成本,   SUM(C2:C100),
    毛利,   销售额 - 成本,
    IF(销售额=0, "无数据", 毛利/销售额)
)
```

同一个计算只算一次（性能），而且公式能读懂了。
这直接对应 ICAEW 的两条原则：把公式写短、算过一次就引用回来。

### GROUPBY / PIVOTBY：公式版的透视表

2024 年进入 Microsoft 365。GROUPBY 做单轴聚合（按地区求和），
PIVOTBY 做双轴（地区 × 月份）。

```excel
=GROUPBY(地区列, 销售额列, SUM)
=PIVOTBY(地区列, 月份列, 销售额列, SUM)
```

相对透视表的优势：源数据变了自动更新，不用手动刷新；
可以在公式层面控制排序、筛选、格式；能被其他公式引用。

2026 年新增 `PERCENTOF` 聚合方式，直接算各组占总体的比例，不用另写公式。
具体参数顺序和可选项以官方文档为准——这组函数还在快速迭代。

### LAMBDA：把重复逻辑变成函数

```excel
=LAMBDA(x, y, (x-y)/y)(本期, 上期)
```

通过「名称管理器」命名后可以全表复用，比如定义一个 `增长率` 函数。
配套的辅助函数有 MAP、REDUCE、SCAN、BYROW、BYCOL。

**判断什么时候该用**：同一段逻辑在表里出现三次以上，就该抽成 LAMBDA。
但也别过头——ICAEW 有一条原则是「能用简单功能达到同样效果时，避免用高级功能」。
一个只有你看得懂的 LAMBDA 嵌套，对接手的人是灾难。

### Power Query：清洗的正确位置

大多数人在工作表里用公式清洗数据，那是错的位置。
Power Query（数据 → 获取和转换）才是：

- 步骤化、可回放、可审计——每一步都记录在「应用的步骤」里
- 源数据更新后一键刷新，不用重做
- 能处理跨文件、跨文件夹的合并
- 处理量级远超工作表公式

**判断标准**：清洗动作要重复做（每月一次报表），就用 Power Query，不要用公式。
一次性的探索才用公式。

**它的边界在哪**：Power Query 的 M 语言是函数式的，做结构化变换（筛选、合并、
透视、拆列、类型转换）很顺；但**复杂的字符串解析在 M 里会变得很啰嗦**，
高度不规则的模式往往要拆成好几个中间步骤绕过去。一旦清洗逻辑开始长出
自定义算法、或者要接着做建模和统计，就该换成 Python。

所以三者的分工是：

| | 用在哪 |
|---|---|
| 工作表公式 | 一次性的探索、临时算个数 |
| Power Query | 要按月重复、要能一键刷新、变换是结构化的 |
| Python | 逻辑复杂、要接建模、要进代码流水线 |

选错的代价不对称：该用 PQ 的地方用了公式，每个月都要重做一遍；
该用 Python 的地方硬用 M，会写出一段没人敢改的东西。

## 二、工程约定：用代码写 Excel 时

这一节的原则来自 ICAEW《Financial Modelling Code》(2024)——
该规范由英格兰及威尔士特许会计师协会发布，通过对比七家机构的建模标准提炼而成。
以下是其中与自动化生成 Excel 最相关的部分，用自己的话转述。

### 用公式，不要把算好的值硬编码进去

```python
# 不好：在 Python 里算完，写死一个数
ws["B10"] = df["销售额"].sum()          # 写进去 5000，源数据一变就成了假数

# 好：让 Excel 自己算
ws["B10"] = "=SUM(B2:B9)"
```

理由：交出去的表是活的。用户改一个输入，所有下游数字应该跟着变。
硬编码的表看起来一样，但改一个数就全错，而且不报错。

这条适用于所有计算——合计、占比、比率、差额。

### 输入、计算、输出分开

假设和输入集中放在一处（或单独一个 sheet），计算区引用它们，输出区引用计算区。

```python
ws["B2"] = 0.05                    # 假设：增长率，集中在假设区
ws["C5"] = "=B4*(1+$B$2)"          # 计算引用假设，不写 =B4*1.05
```

**公式里绝不能出现会变的数字。** 看到 `=B4*1.05` 就问：这个 1.05 是什么、
谁决定的、变了怎么办。它应该是一个有标签的单元格。

### 加检查单元格

ICAEW 叫 `Include a master check`：一个总检查，任何一项对不上就报警。

```python
ws["H1"] = '=IF(ABS(SUM(B5:B14)-B16)<0.01, "OK", "对不上")'
ws["H2"] = '=IF(COUNTIF(A5:A14,"")>0, "有空行", "OK")'
ws["A1"] = '=IF(COUNTIF(H1:H10,"OK")=COUNTA(H1:H10), "全部通过", "⚠ 有检查未通过")'
```

把总检查放在第一屏能看到的位置。检查不通过时表要自己喊出来，
不能指望使用者去发现。

### 引用要可追溯

硬编码的数字必须在旁边注明来源：来自哪个系统、哪一天、哪份文件。
三个月后没人记得那个 1.05 是从哪来的，包括你自己。

### 一致性

同一行的公式应该完全一致（只有引用位置随列变化）。
一行里有一个格子的公式和邻居不一样，那几乎总是 bug ——
可能是有人手工改过某个值。这也是 Excel 错误最常见的形态之一。

生成时用循环写同一个模板，不要一个个单独写。

### openpyxl 的几个必知点

```python
# 读计算结果 vs 读公式本身
wb = load_workbook(f, data_only=True)   # 得到值（但要求文件被 Excel 打开保存过）
wb = load_workbook(f)                    # 得到公式字符串
```

**致命坑**：用 `data_only=True` 打开再保存，**所有公式会被永久替换成值**。
要改一个有公式的文件，绝对不能用 `data_only=True` 打开。

**另一个坑**：openpyxl 写入的公式不带计算结果。文件用 pandas 或其他库读时，
公式单元格会是 None 或公式文本。Excel 打开时才会计算。
所以「生成 → 校验」的链路不能只靠重新读文件，要么用 LibreOffice 重算
（不是所有环境都有），要么在 Python 侧独立算一遍做交叉验证。

**索引**：openpyxl 是 1-based（`cell(row=1, column=1)` 是 A1），
pandas 的 DataFrame 是 0-based。混用时行号差 1，
再加上表头行的偏移，这是错位的经典来源。

**大文件**：读用 `read_only=True`，写用 `write_only=True`，
否则几十万行会吃掉大量内存。

## 三、那些不知道就会中招的坑

### 浮点精度

Excel 用 IEEE 754 双精度浮点，所以 `=0.1+0.2` 不精确等于 `0.3`。
Excel 有个显示层的修正会掩盖大部分情况，但在比较判断里会暴露：

```excel
=IF(A1=B1, "相等", "不等")        # 计算出来的两个 0.3 可能判为不等
=IF(ABS(A1-B1)<0.001, "相等", "不等")   # 这样写
```

**金额比较永远用容差，不用 `=`。** 这条在对账场景尤其重要。

### 日期系统

Excel 把日期存成从某个原点起的天数。Windows 默认 1900 系统，
旧版 Mac Excel 用 1904 系统——**同一个文件在两个系统间传递，日期会差 4 年多**。

1900 系统还有一个著名的历史 bug：Excel 认为 1900 年 2 月 29 日存在
（实际不存在，1900 不是闰年）。这是为了兼容 Lotus 1-2-3 故意保留的。
后果是 1900 年 3 月 1 日之前的日期计算会差一天。业务数据一般不涉及，
但如果看到 1900 年附近的日期，那基本是「空值被当成 0 转成了日期」。

Python 侧转换：

```python
pd.to_datetime(serial, unit="D", origin="1899-12-30")   # 1900 系统
```

注意原点是 1899-12-30 不是 12-31，正是因为上面那个闰年 bug。

### 易失性函数会让大表卡死

`NOW()` `TODAY()` `RAND()` `RANDBETWEEN()` `OFFSET()` `INDIRECT()` `CELL()` `INFO()`

这些函数在**任何**单元格改动时都会重算，并连带触发所有依赖它们的公式重算。
一张几万行的表里放几百个 OFFSET，每敲一个字就卡几秒。

替代方案：`OFFSET` → `INDEX`，`INDIRECT` → 结构化引用或 XLOOKUP。

### 整列引用

`=SUM(A:A)` 看起来省事，但会扫描一百多万行。
几个这样的公式叠加，表就废了。用具体范围或者表格（Ctrl+T）的结构化引用。

### 合并单元格

合并单元格会破坏排序、筛选、透视、公式填充，几乎所有自动化操作都会被它绊倒。

需要视觉上居中的效果时，用「跨列居中」（设置单元格格式 → 对齐 → 水平 → 跨列居中），
它有合并的外观但不破坏数据结构。

### 文本型数字

单元格左上角的绿色小三角。整列是文本时 `SUM` 得 0。
批量转换：选中 → 数据 → 分列 → 直接完成。或者用「选择性粘贴 → 加 → 0」。

从系统导出的 CSV 里，数字前面常有一个不可见的单引号或不间断空格（U+00A0），
`TRIM()` 处理不了 U+00A0，要用 `SUBSTITUTE(A1, UNICHAR(160), "")`。

### 循环引用

Excel 默认会提示，但如果有人开了「启用迭代计算」，循环引用会静默地
产生一个收敛值或者一个随机结果。ICAEW 明确要求避免循环引用——
遇到需要循环的场景（利息资本化这类），用显式的迭代次数而不是让 Excel 自己转。

### 不必要的四舍五入

在中间步骤用 `ROUND()`，误差会一路累积到最后。
**只在最终显示时四舍五入**，用单元格格式而不是 `ROUND` 函数——
格式只改变显示，底层值仍是精确的。

## 四、86% 这个数字

Panko (1998) 的研究：**86% 的电子表格含有错误**。
欧洲电子表格风险兴趣组（EuSpRIG）从 1995 年起持续收录见诸媒体的电子表格事故。

最著名的一起：Reinhart-Rogoff 的经济学论文，Excel 里选区少选了 5 行，
再加上选择性排除数据和非常规加权，把实际 +2.2% 的 GDP 平均增速算成了 −0.1%。
那篇论文当时是全球紧缩政策的主要学术依据。

写这一节不是为了吓人，是为了说明：**检查不是可选项**。
这些错误全都发生在专业人士手上，而且全都是「看起来完全正常」的表格。
